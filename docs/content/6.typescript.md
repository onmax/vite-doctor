Vite Doctor activates its TypeScript rules automatically when the project contains a `tsconfig.json` or TypeScript source files. The recommended preset focuses on unsafe type claims and unvalidated runtime data.

## Install

Add Vite Doctor to any TypeScript project:

```bash
pnpm add -D vite-doctor
```

Run Doctor from the project root:

```bash
pnpm vite-doctor .
```

No framework option or TypeScript-specific configuration is required. JavaScript-only projects do not activate these rules.

## Use the strict preset

The strict preset adds opinionated checks for runtime narrowing, conditional object spreads, and undocumented type assertions:

```bash
pnpm vite-doctor . --extends auto,vite-doctor/typescript/strict
```

It runs every TypeScript rule except opt-in policy rules such as `typescript/strict/no-comments`, which only a `rules` entry turns on.

## Delete comments no tool reads

`typescript/strict/no-comments` (`TS0017`) reports every comment that no tool reads. Nothing checks that such a comment stays true, so it goes stale when the code changes, and agents read it as a fact. The rule is opt-in: no preset turns it on, `strict` included. Name it in `doctor.config.json`:

```json [doctor.config.json]
{
  "rules": {
    "typescript/strict/no-comments": [
      "warn",
      {
        "allow": ["^\\s*provider-message-match:", "^\\s*@generated-by\\b"],
        "apiDocs": "exported"
      }
    ]
  }
}
```

It checks comments in `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, and `.cjs` files, in both `<script>` blocks of a Vue component, in Vue templates, and in JSX, including JavaScript-only projects. It does not check `<style>` blocks or the files Doctor does not scan, such as test folders, `*.test.*` files, fixtures, and generated files.

### What the rule keeps

The rule keeps a comment when a tool reads it, because deleting it would change a build, a check, or a report:

- compiler, linter, formatter, and coverage directives: `@ts-`, `eslint`, `oxlint-`, `doctor-disable` and `doctor-enable` with their `nuxt-` and `vite-` prefixes, `prettier-ignore`, `oxfmt-ignore`, `dprint-ignore`, `biome-ignore`, `/* global */`, `v8 ignore`, `c8 ignore`, `istanbul ignore`, `@vitest-environment`, and `@jsx` pragmas;
- bundler annotations: `#__PURE__`, `#__NO_SIDE_EFFECTS__`, `@vite-ignore`, `@vue-ignore`, and webpack magic comments;
- triple-slash references, `/*!` banners, `@license` and `@preserve` comments, source map comments, and the `#!` line;
- SAFETY notes and the comments that directly continue them, in any form that `typescript/strict/require-safety-comment-for-type-assertion` (`TS0008`) accepts, so the two rules never disagree;
- typed JSDoc, such as `@type {`, `@param {`, and `@template`, in JavaScript files, where TypeScript reads it;
- the same directives in Vue template comments, such as `<!-- eslint-disable-next-line -->`.

### Options

- `allow`: regular expression sources, matched against the comment text without its delimiters. Use it for comments that the project's own tools read. An invalid pattern stops the run with `DOC0020`.
- `apiDocs`: `"exported"` (the default) keeps a JSDoc block directly before an exported declaration and before the members of an exported declaration: interface, type literal, and class members, enum members, and union members. `"none"` reports those too.

Use `overrides` to change the options for some paths, for example to keep API docs only in published packages:

```json [doctor.config.json]
{
  "rules": { "typescript/strict/no-comments": ["warn", { "apiDocs": "none" }] },
  "overrides": [
    {
      "files": ["packages/*/src/**"],
      "rules": { "typescript/strict/no-comments": ["warn", { "apiDocs": "exported" }] }
    }
  ]
}
```

### Adopt it in an existing codebase

Run it with `--since <ref>` so it reports only comments on changed lines. It needs no baseline file:

```bash
pnpm vite-doctor . --since origin/main --max-warnings 0
```

A full run without `--since` lists every old comment. Code that is moved or reformatted brings its comments into the diff. The rule sets each finding's fingerprint from the file path and the comment text, so a `--baseline` file also survives renamed functions and new code above a comment, but rewording a comment makes it new.

### Classify before deleting

Read each comment and put it in one class before you delete it:

- **Tautology**: it repeats what the code says. Delete it.
- **Stale**: it is no longer true. Delete it.
- **Excuse**: it allows a workaround. File an issue for the workaround, then delete it.
- **Decision Record**: it records a non-obvious decision the code cannot show. Move it to the project's decision log, then delete it.

## Run one rule

Use a TypeScript rule ID without selecting a framework:

```bash
pnpm vite-doctor . --rules typescript/boundaries/no-unvalidated-deserialization
```

Doctor returns compact structured output automatically in recognized agent runtimes. Use `--format agent` for a fixed agent contract or `--format json` for the complete machine report.
