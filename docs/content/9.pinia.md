The Pinia Rule Pack checks `defineStore()` calls in Vue, Vite, and Nuxt projects. Pinia is a Vue ecosystem library rather than part of Vue or Nuxt, so the pack activates on its own when Project Inventory contains `pinia` or `@pinia/nuxt`.

## Install and run

Install Vite Doctor in the project:

```bash
pnpm add -D vite-doctor
```

The Recommended Preset runs automatically. It reports store ids that more than one `defineStore()` call registers, setup stores that read each other's state while their setup functions run, state and getters destructured straight from a store, stores called at module scope, and setup-store state that is changed but not returned:

```bash
pnpm vite-doctor .
```

The Strict Preset adds the `use<Id>Store` naming convention, and reports state that components write directly although the store's own action already writes it:

```bash
pnpm vite-doctor . --extends auto,pinia/strict
```

To diagnose one Rule, select it with `--rules`. Strict-only Rules also need the Strict Preset:

```bash
pnpm vite-doctor . --rules pinia/stores/unique-store-id
pnpm vite-doctor . --rules pinia/stores/no-circular-setup-state-read
pnpm vite-doctor . --rules pinia/state/no-store-destructure
pnpm vite-doctor . --rules pinia/stores/no-module-scope-store
pnpm vite-doctor . --rules pinia/stores/no-unreturned-setup-state
pnpm vite-doctor . --extends auto,pinia/strict --rules pinia/stores/store-name-matches-id
pnpm vite-doctor . --extends auto,pinia/strict --rules pinia/state/no-action-bypass
```

## What Doctor reads

Doctor recognizes `defineStore` imported from `pinia`, including aliased and namespace imports. It also recognizes `defineStore` with no import, which is how `@pinia/nuxt` and `unplugin-auto-import` expose it. Calls whose callee resolves to a local declaration or parameter are skipped, including shadowed named, aliased, and namespace imports.

Doctor only compares ids that are string literals, or template literals without expressions. Both `defineStore('cart', ...)` and the object form `defineStore({ id: 'cart', ... })` are read. Ids built from variables or expressions are skipped.

Duplicate ids are compared across the files Doctor scans by default, so tests, fixtures, and generated files are excluded. The comparison spans workspace packages because stores imported from another package can share the app’s Pinia instance. Diagnostics have heuristic confidence: duplicate ids collide only when their definitions use the same Pinia instance. Doctor does not prove that runtime relationship; independent instances can intentionally reuse ids.

## Stores that read each other during setup

Pinia lets stores use each other, but [reading another store during setup can fail](https://pinia.vuejs.org/cookbook/composing-stores.html). Pinia registers a store before running its setup. If eager store calls form a cycle, even a single read can reach an unfinished store, depending on which store is created first. Defer every reported read to a getter or action that runs after setup, or move a `useStore()` call out of setup to break the cycle.

Doctor tracks eager `useXStore()` calls separately from reads of their results, including property access, destructuring, spreads, and calls to Pinia's `storeToRefs()` or Vue's `toRefs()`. It checks inline callbacks that run immediately, such as Vue `watch()` sources and default `watchEffect()` bodies, but not lazy `computed()` getters or uncalled actions. Pinia's `$subscribe()` is available from the start of setup, but `$state` is not. Option stores are not checked.

Doctor reports the affected reads, including in cycles through more than two stores. It evaluates Vite's `import.meta.env.SSR` branches separately so it does not combine server-only and client-only calls into a cycle. It skips branches when it cannot establish their runtime.

Doctor follows named exports and re-exports through relative imports and the `~`, `@`, `~~`, and `@@` aliases. It uses resolved Vite extension order when the plugin provides it. Without that evidence, it skips imports with competing file extensions rather than guessing from defaults. It uses Nuxt's auto-import registrations for `#imports` when available and skips explicit imports it cannot trace. For implicit auto-imports without authoritative registration data, Doctor matches a unique store exported under that name, preferring the caller's workspace package. These matches lower the diagnostic's confidence.

## State written past its action

Pinia [lets components write state directly](https://pinia.vuejs.org/core-concepts/state.html#Mutating-the-state), so the Strict Preset reports it only when the store already has an [action](https://pinia.vuejs.org/core-concepts/actions.html) that writes the same state property: evidence that the store author meant changes to go through it. Doctor reports a property once two or more other files write it directly, at the property's declaration, with each write as a related location, and names the actions that already write it. Call the action, or add one for a change it does not cover yet. Setup stores must still return the state, since Pinia requires it; do not copy it into components.

Doctor reads option stores (`this.items.push()` and `this.$patch({ items })` inside `actions`) and setup stores (writes to a returned `ref()` or `reactive()` inside a returned function). It finds external writes on the result of `useXStore()` in scripts and `<script setup>` templates: assignments, `++`/`--`, `delete`, `v-model`, builtin `Object.assign`, and mutating methods on arrays, Maps, and Sets that the state initializer declares. Writes inside any `defineStore()` call, including other stores' actions, are not reported. Auto-imported stores resolve the same way as for setup-store cycles, and matches by exported name lower the confidence.

Doctor does not count `$patch()` as a direct write: it is Pinia's own API for changing state from outside the store. Writes through refs from `storeToRefs()`, or through an alias such as `const items = cart.items`, are not followed.

## Store inventory

Doctor lists each store's state, getter, and action keys. For option stores it reads the object `state()` returns, `getters`, and `actions`. For setup stores it reads the object the setup function returns, the way Pinia classifies it: a `ref()` or `reactive()` is state, a `computed()` is a getter, and a function is an action. A spread or computed key in that object, or a setup function that does not end in a single object `return`, leaves the inventory incomplete. Rules that would need the missing keys stay quiet and add an evidence gap to the report.

## Destructured state and getters

A store is a `reactive()` object, and Pinia's docs say [it cannot be destructured](https://pinia.vuejs.org/core-concepts/#Destructuring-from-a-Store): each local holds the value it had when setup ran. Doctor reports `const { count } = useCounterStore()`, and destructuring a `const` binding of the store, in `<script setup>`, `setup()`, and setup-store functions, when a key is state or a getter. It names the keys and points at their declarations. Destructuring only actions, `storeToRefs()`, and keys the inventory does not list are not reported, nor is destructuring inside an event handler or other function, where a one-time read can be intended.

## Stores called at module scope

`useXStore()` finds its Pinia through the current app, so a call that runs when a module is first imported throws if `app.use(pinia)` has not run yet, and when the module runs on the server it shares one store across SSR requests ([using a store outside of a component](https://pinia.vuejs.org/core-concepts/outside-component-usage.html)). Doctor reports calls at the top level of a module or an SFC's plain `<script>`. It skips calls inside `<script setup>`, `setup()`, functions and callbacks, and calls that pass a Pinia instance. Recognized prior activation in the same module prevents a startup warning. Creating a Pinia instance without installing or activating it does not count, and prior activation does not isolate SSR requests.

In Nuxt SSR projects, Doctor follows static runtime imports and re-exports back to server-capable app entries recorded by the Nuxt 4 Bridge during Nuxt preparation or build. It warns about shared state when it finds such an entry, even after prior activation. Without current entry evidence, Doctor still checks startup order but does not infer server execution from filenames or plugin configuration.

## Setup-store state that is not returned

Pinia's docs say setup stores [must return all state properties](https://pinia.vuejs.org/core-concepts/#Setup-Stores); state left out is missing from `$state`, `$patch()`, Devtools, and SSR hydration. Doctor reports a top-level `const x = ref()` or `reactive()` when a nested function writes it but the setup function does not return the state itself. An action or computed getter that closes over the state, or a primitive snapshot such as `count.value`, does not expose it as state. Returning a reactive object through `.value` can expose mutations to that object, but it does not expose replacements of the ref's value. A raw object, such as the object in `shallowRef({ count: 0 })` or `ref(markRaw({ count: 0 }))`, is not registered as state when returned through `.value`. A ref read only during setup, a plain variable, and a ref that escapes into another object or call are not reported.
