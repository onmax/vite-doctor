The Pinia Rule Pack checks `defineStore()` calls in Vue, Vite, and Nuxt projects. Pinia is a Vue ecosystem library rather than part of Vue or Nuxt, so the pack activates on its own when Project Inventory contains `pinia` or `@pinia/nuxt`.

## Install and run

Install Vite Doctor in the project:

```bash
pnpm add -D vite-doctor
```

The Recommended Preset runs automatically. It reports store ids that more than one `defineStore()` call registers, and setup stores that read each other's state while their setup functions run:

```bash
pnpm vite-doctor .
```

The Strict Preset adds the `use<Id>Store` naming convention:

```bash
pnpm vite-doctor . --extends auto,pinia/strict
```

To diagnose one Rule, select it with `--rules`. Strict-only Rules also need the Strict Preset:

```bash
pnpm vite-doctor . --rules pinia/stores/unique-store-id
pnpm vite-doctor . --rules pinia/stores/no-circular-setup-state-read
pnpm vite-doctor . --extends auto,pinia/strict --rules pinia/stores/store-name-matches-id
```

## What Doctor reads

Doctor recognizes `defineStore` imported from `pinia`, including aliased and namespace imports. It also recognizes `defineStore` with no import, which is how `@pinia/nuxt` and `unplugin-auto-import` expose it. Calls whose callee resolves to a local declaration or parameter are skipped, including shadowed named, aliased, and namespace imports.

Doctor only compares ids that are string literals, or template literals without expressions. Both `defineStore('cart', ...)` and the object form `defineStore({ id: 'cart', ... })` are read. Ids built from variables or expressions are skipped.

Duplicate ids are compared across the files Doctor scans by default, so tests, fixtures, and generated files are excluded. The comparison spans workspace packages because stores imported from another package can share the app’s Pinia instance. Diagnostics have heuristic confidence: duplicate ids collide only when their definitions use the same Pinia instance. Doctor does not prove that runtime relationship; independent instances can intentionally reuse ids.

## Stores that read each other during setup

Pinia lets stores use each other, but [reading another store during setup can fail](https://pinia.vuejs.org/cookbook/composing-stores.html). Pinia registers a store before running its setup. If eager store calls form a cycle, even a single read can reach an unfinished store, depending on which store is created first. Defer every reported read to a getter or action that runs after setup, or move a `useStore()` call out of setup to break the cycle.

Doctor tracks eager `useXStore()` calls separately from reads of their results, including property access, destructuring, spreads, and calls to Pinia's `storeToRefs()` or Vue's `toRefs()`. It checks inline callbacks that run immediately, such as Vue `watch()` sources and default `watchEffect()` bodies, but not lazy `computed()` getters or uncalled actions. Pinia's `$subscribe()` is available from the start of setup, but `$state` is not. Option stores are not checked.

Doctor reports the affected reads, including in cycles through more than two stores. It evaluates Vite's `import.meta.env.SSR` branches separately so it does not combine server-only and client-only calls into a cycle. It skips branches when it cannot establish their runtime.

Doctor follows named exports and re-exports through relative imports and the `~`, `@`, `~~`, and `@@` aliases. It uses resolved Vite extension order when the plugin provides it. Without that evidence, it skips imports with competing file extensions rather than guessing from defaults. It uses Nuxt's auto-import registrations for `#imports` when available and skips explicit imports it cannot trace. For implicit auto-imports without authoritative registration data, Doctor matches a unique store exported under that name, preferring the caller's workspace package. These matches lower the diagnostic's confidence.
