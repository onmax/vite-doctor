The MCP Rule Pack checks the tools an MCP server defines. A server can work in your own tests and still be rejected later: Anthropic's Connectors Directory flags tools without a title or a safety hint, and clients treat a tool that declares neither `readOnlyHint` nor `destructiveHint` as destructive. A tool can also answer with more tokens than its data needs, such as indented JSON. The pack finds those problems in source, before you submit.

It activates on its own when Project Inventory contains `h3-mcp`, `okmcp`, `nitro-mcp-toolkit`, `@nuxtjs/mcp-toolkit`, `vite-hub`, `@vite-hub/mcp`, `@modelcontextprotocol/sdk`, or `@modelcontextprotocol/server`. It also activates for every workspace package when the run reads a server's tools, through `--mcp-url`, the plugin's `mcp` option, or a Doctor Extension, so a repository that only watches a deployed server needs no MCP package.

## Install and run

Install Vite Doctor in the project:

```bash
pnpm add -D vite-doctor
```

The Recommended Preset runs automatically:

```bash
pnpm vite-doctor .
```

To diagnose one Rule, select it with `--rules`:

```bash
pnpm vite-doctor . --rules mcp/tools/require-annotation-title
```

## What Doctor reads

Doctor builds an inventory of tool definitions from these calls:

| Library                                                     | Definition                                                                                                      |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `h3-mcp`, `okmcp`                                           | `defineTool()` imported from the package                                                                        |
| `nitro-mcp-toolkit`                                         | `defineMcpTool()` imported from the package                                                                     |
| `@nuxtjs/mcp-toolkit`                                       | `defineMcpTool()`, imported or auto-imported                                                                    |
| `vite-hub`, `@vite-hub/mcp`                                 | `defineMcpTool()` imported from `vite-hub/mcp` or `@vite-hub/mcp`                                               |
| `@modelcontextprotocol/sdk`, `@modelcontextprotocol/server` | `server.registerTool(name, config, handler)` on a `const` initialized with `new McpServer()` from an SDK import |

A local function that happens to share one of these names is skipped.

Both toolkits name a tool discovered under `server/mcp/tools/` after its file, and fill its top-level `title` from the file name. Doctor applies the same naming to default exports in that directory. Neither toolkit copies that title into `annotations`, which is why the inventory reads the two separately. ViteHub names a tool after its path below `mcp/tools/`, without the extension or a trailing `/index`. It ignores the definition's `name` and fills no title.

Annotations can be an object literal or spread shared objects into one. Doctor follows a spread to a `const` in the same file, to an export of a relatively imported file, and to a unique export in an auto-imported `server/utils` or `shared/utils` file. When it can't follow a spread or read a key, it reports nothing for that tool rather than guess.

An annotation title must be a non-empty string. A safety hint must set `readOnlyHint` or `destructiveHint` to `true`; `false`, `undefined`, and values of the wrong type don't satisfy the Connector criteria. The MCP0002 fix follows the hints a tool declares: with `readOnlyHint: false` it asks for `destructiveHint: true`, and with both hints `false`, which MCP uses for tools that only add data, it explains that the Directory review will still flag the tool. Doctor follows statically readable constant values and respects the order of spread overrides. When a relevant value is only known at runtime, it skips that Rule for the tool.

Doctor looks for indented JSON returned directly by the handler or in a `{ type: 'text', text: … }` block in its returned `content` array. It follows returned helper calls up to two levels deep, including a shared `toStructuredResult()` in `server/utils`. Metadata, structured content, unrelated callbacks, and indents Doctor can't read are skipped. To compact the JSON without changing which data is serialized, remove only the third argument to `JSON.stringify()` and keep the replacer.

From source alone, a tool that a Nitro hook or plugin changes at runtime is diagnosed as written. When the Doctor Run also reads the server's `tools/list` (see below), MCP0001, MCP0002, and MCP0003 check the tool the server sends instead. A tool the server sends under the name of exactly one source definition is reported at that definition when its `tools/list` entry fails, and not at all when the entry passes, even if the source would fail. A tool the server sends with no matching definition is reported at the project root. These Diagnostics are `runtime-backed`, and their `data` holds the server, the tool, and the library findings behind them. A source definition the server doesn't send is checked from source as before.

`mcp/tools/valid-annotations` (MCP0010) reads only the `tools/list`. It reports a tool whose `annotations` are not an object, that set `title` to something other than a string or `readOnlyHint`, `destructiveHint`, `idempotentHint`, or `openWorldHint` to something other than a boolean, or that hold a serialized Zod schema (`_def`, `~standard`, `_zod`). The MCP TypeScript SDK's client rejects the whole `tools/list` response in the first two cases, which loses every tool on that page. Fields `ToolAnnotations` doesn't define are allowed, and clients drop them. A serialized schema is usually one passed where `server.tool()` expects annotations, as when a Zod object that isn't a raw shape lands there with older SDK versions, and the tool then ships with an empty input schema. When MCP0010 reports a tool, MCP0001 and MCP0002 don't report its missing title and hints too.

## Read a running server

Source shows the tools as written; a running server shows the tools a client gets. Point Doctor at a Streamable HTTP endpoint and it sends the requests a client sends when it connects, `initialize` and every page of `tools/list`, and keeps the result as Runtime Evidence for the Doctor Run:

```bash
pnpm vite-doctor . --mcp-url http://localhost:3000/mcp
```

Run it in an empty directory to check only the server. The text report says `Checked: MCP server <origin>`. JSON and agent reports name the server in `subject.mcpServers`; JSON has `framework: null`, while the agent report has `project: null`. Doctor activates only the MCP Rule Pack and lists the server's origin as that pack's `activatedBy`. Rerun commands keep the original scan directory and repeat `--mcp-url` without adding `--framework`.

Both flags repeat. Every `--mcp-header` goes to every `--mcp-url`:

```bash
pnpm vite-doctor . \
  --mcp-url http://localhost:3000/mcp \
  --mcp-url https://staging.example.com/mcp \
  --mcp-header "Authorization: Bearer $MCP_TOKEN"
```

In the Vite plugin, pass the same list as `mcp`. In dev, a path such as `/mcp` resolves against the dev server once it listens:

```ts [vite.config.ts]
doctor({ run: "serve", mcp: [{ url: "/mcp" }] });
```

A build has no dev server, so a path there fails the build as a config error. Nuxt runs Vite in middleware mode, where Vite doesn't know the server's URL, so in a Nuxt app pass an absolute URL such as `http://localhost:3000/mcp`. Each entry also takes `headers` and a `serverName` for the client-configured alias and report label. The name announced by the server is a report label, not a client alias.

Use the final MCP endpoint URL: Doctor does not follow redirects. Reports show only the endpoint origin, except rerun commands, which omit fragments and replace credentials and query strings with `<redacted>`. Rerun commands keep `/`, `/mcp`, `/sse`, `/v1/sse`, and `/github-copilot/mcp` verbatim and redact other paths because they can contain secrets.

Headers often carry tokens, so `mcp` is not part of Doctor config: `doctor.config.json` and the `doctor` key of `vite.config.*` don't accept it, reports never include header values, and rerun commands name each header with a `<redacted>` value. The agent report's `placeholders` field says what to put back.

Doctor never probes `/mcp` on its own. When it can't read a server (the connection fails, the server answers 401, or it returns a JSON-RPC error), the report is `incomplete` and the evidence gap names the URL and the reason. When an MCP Rule checks a list, the report shows `Evidence used: tools/list of the MCP server at <origin>, <n> tools`; JSON and agent reports list it under `evidenceUsed`. If filters or Rule settings skip every MCP Rule that reads the list, a fetched list does not appear as evidence used. If an explicit `extends` list leaves out the MCP Rule Pack and no client Rule checks the list project-wide, the report is `incomplete` too. File overrides can check tools with matching source definitions; the report labels this evidence use as `file overrides only` without clearing the project-wide gap. See [Run in CI](#run-in-ci).

A Doctor Extension can contribute tool lists too. Any Runtime Evidence contributor that returns `{ mcpServers: [{ name, url, initialize, tools }] }` feeds the same checks, without a URL or a network request. It can also supply `clientAlias` if the client configuration is known. This is how ViteHub hands Doctor the tools it already knows:

```ts [vitehub-doctor-extension.ts]
import { defineDoctorExtension } from "vite-doctor/extension";
import type { McpTool } from "vite-doctor/mcp";

export function vitehubMcpEvidence(tools: McpTool[]) {
  return defineDoctorExtension({
    name: "vitehub/mcp-evidence",
    setup(api) {
      api.registerRuntimeEvidenceContributor({
        name: "vitehub",
        contribute: () => ({ mcpServers: [{ name: "vitehub", tools }] }),
      });
    },
  });
}
```

`readMcpServers(runtimeEvidence)` from `vite-doctor/mcp` collects the servers of every contributor, so an extension's own Rules can read them as well.

## Client limits

A tool that passes the MCP specification can still lose something in a client. Claude Code leaves out a tool whose schema isn't valid draft 2020-12, VS Code omits one that isn't valid draft-07, Copilot Studio drops one with `$ref`, and Codex removes `minimum` and `maxLength` before the model sees the schema. None of this is an error on the server: `tools/list` answers normally, and the tool is missing or different only in that client.

These Rules check the `tools/list` Doctor reads as Runtime Evidence, whichever way it arrives: the `mcp` option or `--mcp-url`, a path such as `/mcp` resolved against the Vite dev server, or a Doctor Extension contributing `{ mcpServers }`. Without MCP evidence they report nothing and add no evidence gap. A server Doctor couldn't read is already an evidence gap, so they skip it.

| Rule                                 | Code    | Preset      | What the client does                                                                                                      |
| ------------------------------------ | ------- | ----------- | ------------------------------------------------------------------------------------------------------------------------- |
| `mcp/clients/no-excluded-tool`       | MCP0005 | Recommended | Leaves the tool or the whole server out, or the request fails                                                             |
| `mcp/clients/no-truncated-text`      | MCP0006 | Recommended | Cuts a description, the instructions, or the schema                                                                       |
| `mcp/clients/no-rewritten-schema`    | MCP0007 | Strict      | Renames the tool, replaces an empty description, reads an `enum` as a string, or flattens the root                        |
| `mcp/clients/no-stripped-constraint` | MCP0008 | Strict      | Drops a constraint a model can get wrong that no description states, shrinks a large schema, or deletes a root combinator |
| `mcp/clients/no-reduced-context`     | MCP0009 | Strict      | Shows the model less of the server: no instructions under tool search, or more tools than it sends                        |

Doctor reports one Diagnostic per server, tool, and code. Its message names each client and what it does, with measured lengths where there are any, and its evidence cites each client's source by URL with the date it was checked. The quoted source stays in the Diagnostic's `data.findings[].source.quote`. Text and agent reports name the tool as the Diagnostic's `subject` and print a one-line `brief` for each tool. Severity is the worst of the clients' effects (`error` when a client leaves the tool out, `warn` when content is lost, `info` when it is rewritten) and confidence is `runtime-backed`, or `heuristic-medium` when the consequence is inferred from a client's source or a forum answer. When exactly one tool of the same name is defined in a package that depends on an MCP library, the Diagnostic points at its name; otherwise it points at the project root with a fingerprint built from the server and tool.

Each finding in the message lists at most five JSON Pointers. The JSON and agent reports carry every finding under the Diagnostic's `data`, and SARIF under `results[].properties.data`, in the same shape `checkMcpClientLimits` returns, so an agent can group them by client or JSON Pointer without parsing the message:

```json
{
  "code": "MCP0008",
  "data": {
    "server": { "name": "Nuxt", "url": "https://nuxt.com" },
    "tool": "get-changelog",
    "findings": [
      {
        "client": "codex",
        "rule": "codex/dropped-constraints",
        "effect": "stripped",
        "severity": "info",
        "confidence": "high",
        "tool": "get-changelog",
        "pointer": "/inputSchema/properties/limit",
        "affectedPointers": ["/inputSchema/properties/limit"],
        "message": "...",
        "fix": "...",
        "source": { "url": "...", "kind": "source", "checked": "...", "quote": "..." }
      }
    ]
  }
}
```

`server.url` is the endpoint origin, as elsewhere in the report. A server-level finding has no `tool`. The source Rules (MCP0001 to MCP0004) set `data.tool` only when Doctor can determine the tool name statically.

Missing titles and safety hints stay with MCP0001 and MCP0002, and a client renaming a tool whose source definition already breaks MCP0003 is not reported again. A tool defined only on the server keeps its client renames, since a client can limit names more strictly than MCP.

### Check tools in your own tests

The checks come from `@loadsheet/mcp`, which `vite-doctor/mcp` re-exports, so an end-to-end test can run them on what the server really returns, including each `tools/call` result, which Doctor never calls on its own. `checkMcpToolList` returns the Diagnostics Doctor would report for the list, each with its code, Rule, message, fix, and the client findings behind it. `checkMcpClientLimits` and `checkMcpToolResult` return the client findings, each with the client, the rule, a message, a fix, and its source:

```ts [tests/e2e/mcp.spec.ts]
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/sdk/client/streamableHttp.js";
import { checkMcpClientLimits, checkMcpToolResult } from "vite-doctor/mcp";
import { expect, test } from "vitest";
import { sampleArguments } from "./mcp-arguments";

test("every client gets every tool intact", async () => {
  const client = new Client({ name: "e2e", version: "1.0.0" });
  await client.connect(new StreamableHTTPClientTransport(new URL("http://localhost:3000/mcp")));
  const { tools } = await client.listTools();
  const lost = (finding: { severity: string }) => finding.severity !== "info";

  expect(checkMcpClientLimits({ tools }, { serverName: "portal" }).filter(lost)).toEqual([]);
  for (const tool of tools) {
    const result = await client.callTool({
      name: tool.name,
      arguments: sampleArguments[tool.name],
    });
    expect(checkMcpToolResult(result, { tool }).filter(lost)).toEqual([]);
  }
});
```

Pass `clients: ["claude-code", "vscode"]` to check only the clients you support, and `codes` to `checkMcpToolList` to report only some Diagnostic Codes.

## Run in CI

`--mcp-url` uses the usual [exit codes](/cli#exit-codes). An incomplete run exits `3` even if the Diagnostics it did report would otherwise fail the job:

| Result                                                                     | Exit code |
| -------------------------------------------------------------------------- | --------- |
| Incomplete: Doctor can't read the server or didn't check the tools it read | `3`       |
| Complete with a `blocker` or `error`, such as a client leaving out a tool  | `1`       |
| Complete with more warnings than the configured `--max-warnings` limit     | `1`       |
| Complete with neither of the above; `info` never affects the exit code     | `0`       |

Strict Rules can add warnings as well as `info` Diagnostics. For example, the Strict Preset warns when a server exceeds VS Code's tool limit. With `--max-warnings 0`, any warning fails a complete run; without a warning limit, warnings alone don't fail it.

The server's tools activate the MCP Rule Pack, so the Recommended Preset runs even in a repository without an MCP package, and `--strict` runs the Strict Preset. An explicit `extends` list selects only what it names: add `auto`, or `mcp/recommended` (`mcp/strict`), to it. A CLI `--extends` replaces the configured list, so repeat your selectors there, for example `--extends design-system/recommended,mcp/recommended`. Otherwise the run is `incomplete` and exits `3`.

Start the server in the background, wait until it answers, then point Doctor at it:

```yaml [.github/workflows/checks.yml]
- run: pnpm install --frozen-lockfile
- name: Check the MCP server
  run: |
    nohup pnpm dev --port 3000 > dev.log 2>&1 &
    for i in $(seq 1 60); do curl -sf -o /dev/null http://localhost:3000/ && break; sleep 1; done
    pnpm vite-doctor . --mcp-url http://localhost:3000/mcp --max-warnings 0
```

To check a deployed server, pass its token from a secret. Reports and rerun commands never include header values:

```yaml [.github/workflows/checks.yml]
- name: Check the staging MCP server
  run: |
    pnpm vite-doctor . --mcp-url https://staging.example.com/mcp --mcp-header "Authorization: Bearer $MCP_TOKEN" --max-warnings 0
  env:
    MCP_TOKEN: ${{ secrets.MCP_TOKEN }}
```
