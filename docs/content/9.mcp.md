The MCP Rule Pack checks the tools an MCP server defines. A server can work in your own tests and still be rejected later: Anthropic's Connectors Directory flags tools without a title or a safety hint, and clients treat a tool that declares neither `readOnlyHint` nor `destructiveHint` as destructive. The pack finds those problems in source, before you submit.

It activates on its own when Project Inventory contains `h3-mcp`, `okmcp`, `nitro-mcp-toolkit`, `@nuxtjs/mcp-toolkit`, `@modelcontextprotocol/sdk`, or `@modelcontextprotocol/server`.

## Install and run

Install Vite Doctor in the project:

```bash
pnpm add -D vite-doctor
```

The Recommended Preset runs automatically:

```bash
pnpm vite-doctor .
```

To diagnose one Rule, select it with `--rules`:

```bash
pnpm vite-doctor . --rules mcp/tools/require-annotation-title
```

## What Doctor reads

Doctor builds an inventory of tool definitions from these calls:

| Library                     | Definition                                                                         |
| --------------------------- | ---------------------------------------------------------------------------------- |
| `h3-mcp`, `okmcp`           | `defineTool()` imported from the package                                           |
| `nitro-mcp-toolkit`         | `defineMcpTool()` imported from the package                                        |
| `@nuxtjs/mcp-toolkit`       | `defineMcpTool()`, imported or auto-imported                                       |
| `@modelcontextprotocol/sdk` | `server.registerTool(name, config, handler)` in a file that imports the SDK server |

A local function that happens to share one of these names is skipped.

Both toolkits name a tool discovered under `server/mcp/tools/` after its file, and fill its top-level `title` from the file name. Doctor applies the same naming to default exports in that directory. Neither toolkit copies that title into `annotations`, which is why the inventory reads the two separately.

Annotations can be an object literal or spread shared objects into one. Doctor follows a spread to a `const` in the same file, to an export of a relatively imported file, and to a unique export in an auto-imported `server/utils` or `shared/utils` file. When it can't follow a spread or read a key, it reports nothing for that tool rather than guess.

Doctor reads source only, so a tool that a Nitro hook or plugin changes at runtime is diagnosed as written.
