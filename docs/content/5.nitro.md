Use Nitro rules for server handlers, request helpers, runtime config access, and boundaries between server code and client-only APIs.

## Install

Add Vite Doctor to the project:

```bash
pnpm add -D vite-doctor
```

For a Vite-hosted Nitro project, register the Vite plugin:

```ts [vite.config.ts]
import { doctor } from "vite-doctor";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [doctor()],
});
```

Set `framework: "nitro"` only when Doctor cannot identify the Nitro app automatically.

Run Doctor directly when you want a focused Nitro Doctor Run:

```bash
pnpm vite-doctor . --framework nitro --rules nitro
```

## Configure

Keep Nitro rule policy on the Doctor surface that runs the project:

```ts [vite.config.ts]
import { doctor } from "vite-doctor";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    doctor({
      extends: ["nitro/recommended"],
      config: {
        rules: {
          "nitro/request/prefer-validated-body": "warn",
        },
      },
    }),
  ],
});
```

## Pick the right reference

Nitro rules focus on request validation, runtime config, internal fetches, redirects, and server-only execution. Start in [Nitro rules](/nitro/rules) when a diagnostic begins with `nitro/`.

In Nuxt projects, Nitro diagnostics can appear during a Nuxt Doctor run because Nuxt owns server routes through Nitro.

## Fix a diagnostic

Open the rule page from the reported rule ID and re-run only the failing Nitro rule while you edit:

```bash
pnpm vite-doctor . --framework nitro --rules nitro/request/prefer-validated-body
```

Prefer framework helpers such as `readValidatedBody(event, schema.parse)` when a rule points at request parsing or validation.
