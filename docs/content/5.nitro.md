Use Nitro rules for server handlers, request helpers, runtime config access, and boundaries between server code and client-only APIs.

Doctor resolves the installed Nitro package and follows it to the H3 instance Nitro owns. Runtime-specific rules activate from those exact versions, including prereleases, while unresolved or custom package identities suppress version-specific advice instead of guessing.

## Install

Add Vite Doctor to the project:

```bash
pnpm add -D vite-doctor
```

For a Vite-hosted Nitro project, register the Vite plugin:

```ts [vite.config.ts]
import { doctor } from "vite-doctor";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [doctor()],
});
```

Set `framework: "nitro"` only when Doctor cannot identify the Nitro app automatically.

Run Doctor directly when you want a focused Nitro Doctor Run:

```bash
pnpm vite-doctor . --framework nitro --rules nitro
```

Check a Nitro 2 project against Nitro 3 before changing dependencies:

```bash
pnpm dlx vite-doctor migrate . --to nitro@3
```

The migration command keeps Nitro 3 and H3 v2 source changes with the dependency change that activates them, then lists checks that must wait until the new runtime is installed. It does not modify source or package files.

## Configure

Keep Nitro rule policy on the Doctor surface that runs the project:

```ts [vite.config.ts]
import { doctor } from "vite-doctor";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    doctor({
      extends: ["nitro/recommended"],
      config: {
        rules: {
          "nitro/request/prefer-route-method-suffix": "warn",
        },
      },
    }),
  ],
});
```

## Pick the right reference

Nitro rules focus on runtime config, internal fetches, route files, caching, and server-only execution. Start in [Nitro rules](/nitro/rules) when a diagnostic begins with `nitro/`.

Request validation, redirects, HTTP errors, and the H3 v2 migration rules live in the [H3 Rule Pack](/h3). Their ids begin with `h3/` and their codes with `H3`. Nitro and Nuxt projects activate that pack automatically, so a Doctor Run on a Nitro project reports both. The rules that were `NITRO0003` to `NITRO0007` and `NITRO0015` to `NITRO0018` moved there, and the [H3 page](/h3#moved-from-nitro) maps the old codes to the new ones.

In Nuxt projects, Nitro diagnostics can appear during a Nuxt Doctor run because Nuxt owns server routes through Nitro.

## Fix a diagnostic

Open the rule page from the reported rule ID and re-run only the failing Nitro rule while you edit:

```bash
pnpm vite-doctor . --framework nitro --rules nitro/request/prefer-route-method-suffix
```

Prefer framework helpers, such as a method suffix in the route file name, over hand-written checks when a rule points at one.
