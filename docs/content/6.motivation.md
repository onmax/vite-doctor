title: Motivation
description: Why Doctor exists for the Vue, Vite, Nitro, and Nuxt ecosystem.
---

Doctor exists because framework bugs often look correct in ordinary code review.

Vue and Nuxt applications have rules that depend on runtime boundaries, compiler behavior, auto-imports, hydration, server handlers, module conventions, and generated project metadata. Generic lint rules catch syntax and style drift, but they usually do not know whether a composable runs in the right phase, whether a value crosses the server-client boundary safely, or whether a module API is stale.

## Inspired by rule visibility

React Doctor showed that developers benefit from a visible rule catalog: one place to search checks, understand why they exist, and copy rule ids into local or automated workflows.

Doctor applies that idea to the Vue ecosystem:

- Vue rules for reactivity, computed values, watchers, templates, SSR, and security.
- Vite rules for env exposure, define constants, public assets, workers, plugins, HMR, SSR entries, and dev-server safety.
- Nitro rules for request validation, event-aware helpers, runtime config, and server boundaries.
- Nuxt rules for auto-imports, fetching, routing, runtime config, hydration, module overlays, and content/docs conventions.

## Keep the workflow simple

Humans run the CLI or the Nuxt command. Agents use the existing Nuxt MCP endpoint when a running app can expose read-only reports.

The docs keep those workflows separate:

- [Installation](/installation) routes people to the right entry point.
- [Nuxt AI](/nuxt/ai) explains the MCP workflow for agents.
- [Rules](/rules/nuxt) exposes searchable rule references with one page per rule.
